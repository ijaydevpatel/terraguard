# D08 - Ethics and data statement

Draft for the dissertation front matter.

## Human participants

None. No survey, interview, observation or user study forms any part of this work. No personal
data is collected, processed or stored at any stage.

One human input is planned: an independent review of a sample of severity labels (T112) by a
supervisor or peer. That reviewer is acting in a professional capacity on the author's own
research artefacts, and no data about the reviewer is recorded. Only the label decisions and
the reasons for disagreement are kept.

The programme's ethics deadline has not yet been confirmed (T012). If the review requires an
application, it must be lodged before T112 goes ahead.

## What the data is

All data is generated by the author, in infrastructure owned by the author, for this study.
Nothing is scraped, purchased, donated or reused from a third party.

The dataset has two tables. `observations.csv` holds one row per scenario run;
`findings.csv` holds one row per control violation raised. At the time of writing these
contain 26 and 32 rows, all from offline fixtures.

There was no viable alternative to generating it. The labels this project needs - a drift
event paired with a policy outcome and a severity band, under a known ground truth - do not
exist in any public dataset. TerraGoat and similar corpora supply insecure Terraform, but not
the run-level ground truth that makes a detection figure meaningful.

## Credentials and secrets

No real credential exists anywhere in this repository or its history.

Fixtures are deliberately insecure, because that is what they are for, but every secret in
them is synthetic and marked `TERRAGUARD_TEST_SECRET_nnn`. Where an AWS-shaped key is needed,
the value is AWS's own published documentation placeholder, and the account number is
`000000000000`. Ten separate audits have confirmed nothing real is exposed.

Three controls enforce this rather than relying on care:

- `gitleaks` runs in pre-commit and again in CI.
- A custom commit guard rejects any `.tfstate`, state backup or saved plan.
- Redaction happens on write. The collector never puts an unredacted plan on disk: the binary
  plan and raw JSON live in a temporary directory removed in a `finally` block.

Redaction preserves shape rather than deleting values - `[REDACTED]:len=n:sha256:…` - so the
same secret can be correlated across runs without the value being recoverable. A final
`assert_clean()` gate runs on the finished report, because the report is the artefact that
actually leaves the machine.

## Cloud resources and cost

Experiments will run in a dedicated AWS sandbox account holding nothing else, in
`us-east-1`, tagged `environment = test`. Budget alarms are defined as code at $5 and
$15. Everything is destroyed at the W12 teardown, and zero spend is confirmed and recorded.

`prevent_destroy` is deliberately switched off on the state bucket. Production guidance would
require it; a research environment that must be torn down cleanly is better without it. This
is recorded as a stated deviation rather than left as an oversight.

At the time of writing the account does not exist, so no cloud resource has been created and
no cost has been incurred.

## Dual-use

The tool detects insecure Terraform state handling. The same knowledge describes how to leave
state exposed.

The risk is low and worth stating anyway. Nothing here is novel offensive capability: every
control is traced to published HashiCorp, AWS Config or GitHub Actions documentation, and the
failure modes are already well described in that documentation and in the literature review.
The tool reads configuration and reports; it never modifies infrastructure, never exfiltrates
state, and has no remediation capability. Autonomous remediation is an explicit exclusion in
§1.4, and that exclusion is partly an ethical one.

The injection scripts are the sharper end. They deliberately create insecure configurations -
an open security group, a disabled trail - and are written to run against one specific
author-owned sandbox with pre-flight checks that refuse to run anywhere else. They are
research instruments for a controlled environment, not a toolkit.

## Honesty about what has been demonstrated

Two claims in this project are weaker than they may first appear, and both are stated in the
results rather than left for a reader to discover.

The drift half of the dataset is empty. Every drift capability has been exercised against
fixtures, because the AWS baseline has never been deployed. Any claim about detecting
infrastructure drift is currently supported by synthetic plan JSON alone.

The severity comparison is circular. The labels come from the same rubric that the
deterministic baseline implements, so that baseline scores 1.0 by construction and cannot be
compared with the trained models. This is recorded openly as risk R20, and the RQ2 answer
stays open until external labels exist.

## Availability

Code, scenario manifests, the generated dataset and the reproducibility record are in the
project repository. No component is withheld, and there is no confidential or third-party
material in it.
